## Purpose

Позволяет воспроизводимо запускать SDD-подходы на подготовленных задачах и отдельно проверять результат каждого прогона.

## ADDED Requirements

### Requirement: Пакеты задачи, подхода, харнеса и оценки
Система MUST принимать независимые пакеты задачи, SDD-подхода, харнеса и оценки.

#### Scenario: Состав задачи
- **WHEN** запускается задача
- **THEN** исполнитель получает копию проекта, контекст и запрос, а тесты хранятся отдельно.

#### Scenario: Выбор харнеса
- **WHEN** запускаются одна задача и подход с разными харнесами
- **THEN** в каждом прогоне используется выбранный харнес, а его имя сохраняется в результате.

#### Scenario: Выбор оценщика
- **WHEN** прогон запускается с пакетом оценки
- **THEN** оценка выполняется выбранным пакетом, а её имя сохраняется отдельно от результата проверки.

#### Scenario: Детерминированный сценарий
- **WHEN** набор сценариев проверяется без вызова модели
- **THEN** эталонное решение каждого сценария проходит проверку, а версия с дефектом отклоняется, без обращения к сети и сторонним пакетам.

### Requirement: Изолированная рабочая копия
Система MUST создавать новую рабочую копию для каждого прогона.

#### Scenario: Повторные прогоны
- **WHEN** одна задача запускается дважды
- **THEN** изменения первого прогона не попадают во второй.

### Requirement: Независимая оценка
Система MUST выполнять проверку результата отдельным процессом и сохранять исходы этапов.

#### Scenario: Успешное решение
- **WHEN** исполнитель и проверка завершаются с кодом 0
- **THEN** результат имеет статус passed.

#### Scenario: Ошибка проверки
- **WHEN** проверка возвращает ненулевой код
- **THEN** результат имеет статус failed.

### Requirement: События запросов и доступный usage
Система MUST сохранять доступные события запросов и usage с указанием источника и отсутствующих данных.

#### Scenario: Usage только на уровне хода
- **WHEN** харнес сообщает usage только по завершении хода
- **THEN** результат содержит запись о ходе с пометками reported и missing, фиксирует точность и источник usage, а расход отдельного запроса помечает как missing.

#### Scenario: Телеметрия недоступна
- **WHEN** у харнеса нет адаптера телеметрии или адаптер завершился ошибкой
- **THEN** отсутствие данных сохраняется с указанием причины, а исходный журнал не скрывается.

### Requirement: Фазы и готовность намерения
Система MUST фиксировать фазы прогона и момент готовности намерения исполнителя.

#### Scenario: Пакет подхода задаёт маркер намерения
- **WHEN** в пакете подхода задан маркер намерения и файл по этой маске появился в рабочей копии
- **THEN** результат содержит признак готовности и время от старта исполнителя.

#### Scenario: Маркер не появился
- **WHEN** файл по маске не появился за прогон или маркер не задан
- **THEN** готовность намерения не подтверждается, а расход по фазам помечается как недоступный.

### Requirement: Отдельная оценка моделью
Система MUST выполнять отдельную оценку моделью по инструкциям и эталону пакета задачи, не изменяя статус прогона.

#### Scenario: Корректный ответ оценщика
- **WHEN** оценщик вернул числовой score от 0 до 1 и непустой verdict
- **THEN** оценка сохраняется отдельно от результата проверки и не влияет на статус прогона.

#### Scenario: Некорректный ответ оценщика
- **WHEN** ответ оценщика не содержит score в допустимом диапазоне или verdict
- **THEN** оценка помечается как invalid_output, а журнал оценщика сохраняется.

### Requirement: Изоляция закрытых проверок и эталонов
Система MUST запускать проверку и эталон вне рабочей копии и проверять их недоступность исполнителю.

#### Scenario: Копия эталона в рабочей копии
- **WHEN** файл рабочей копии совпадает по содержимому с файлом закрытой проверки или эталона
- **THEN** результат явно перечисляет такую копию.

#### Scenario: Утечка пути через окружение
- **WHEN** окружение исполнителя содержит путь к пакету задачи
- **THEN** результат перечисляет такие переменные, а расположение проверки фиксируется как внешнее по отношению к рабочей копии.

### Requirement: Пошаговый протокол подхода
Система MUST поддерживать подход, задающий последовательность шагов, и MUST выполнять каждый шаг отдельным запуском исполнителя.

#### Scenario: Шаг не оставил обязательный артефакт
- **WHEN** шаг объявляет обязательный артефакт, а после его завершения файла нет
- **THEN** протокол фиксирует неудавшийся шаг, оставшиеся шаги пропускаются, а исход прогона — FAIL_PROCESS.

#### Scenario: Контекст между шагами не переносится
- **WHEN** подход объявляет несколько шагов
- **THEN** каждый шаг запускается новым процессом исполнителя, а состояние переносится только через файлы рабочей копии.

#### Scenario: Расход по шагам
- **WHEN** исполнитель сообщает usage
- **THEN** результат содержит время и расход по каждому шагу отдельно, а отсутствующие данные помечаются как missing.

### Requirement: Терминальный исход и сводка по серии прогонов
Система MUST присваивать каждому прогону один терминальный исход и сводить серию прогонов в общие счётчики.

#### Scenario: Приоритет инфраструктурного отказа
- **WHEN** любой этап прогона завершился по таймауту или ошибкой запуска
- **THEN** исход прогона сообщает TIMEOUT или INFRA_ERROR, а не продуктовый вердикт.

#### Scenario: Нарушение SDD-протокола
- **WHEN** пакет подхода задаёт маркер намерения, но он за прогон не появился
- **THEN** исход прогона FAIL_PROCESS, даже если проверка продукта пройдена.

#### Scenario: Сводка серии
- **WHEN** серия прогонов сводится в отчёт
- **THEN** отчёт содержит N_started, N_completed, N_graded, N_pass, покрытие оцениванием и разбивку по подходу, харнесу и задаче, а отсутствующий расход не считается нулевым.
